Irregularities, defects and traps — flagged, with what was done about each

The brief asks for irregularities to be flagged rather than smoothed over. These are ordered by how much damage they could do.

1. The portal error you hit: "Predicted values must be in range [0, 1]"

Diagnosis. The official spec asks for a single-band float32 raster with values in [0, 1] [OFFICIAL, competition page 967]. Two writing habits violate it while looking correct on screen: a float32 sentinel such as -3.4028235e38 (survives as an outlier inside the valid footprint), and a NaN nodata tag (the reader returns NaN, which is not in [0, 1]). The defective artifact from the earlier session — gems32-h19-5-smoothmaxcov-44090.tif — is one of these, and it is quarantined by standing rule: never ship, never re-emit.

What is done about it. One writer, one code path, and the file is re-opened from disk and re-counted before anything is published (grid.check_submission). The current file reports nodata = null, nan_count = 0, n_outside_0_1 = 0, all_finite = true. The two mechanisms are structurally absent, not merely avoided.

Reported in full, because the numbers above are only trustworthy if the failures are visible.

3. The registry uniqueness tripwire is density-blind — a shared-tool defect, fixed and reported

Defect. The brief's tripwire is "> 70 % of your dots within 3 px of one registry raster's dots ⇒ duplicate". Measured here: 13gems_20261001_r13-lattice-s5_v2 carries 206,895 dots, which dilates to 112 % of the 5.17 M-cell footprint, so its 3 px neighbourhood covers the map and any emission scores ≈ 1.0 on the tripwire.

Proof, not assertion. A uniform-random 1,660-dot control (build/controls/poisson_1660_seed7.tif, seed 7) scores dot_overlap_within_kernel = 0.9982 against that same raster. A tripwire that fires on Poisson noise cannot certify a duplicate.

Fix (in scripts/check_uniqueness.py, reported here rather than forked). The verdict now additionally requires a symmetric overlap — the Jaccard index of the two 3 px-dilated dot masks, |A ∩ B| / |A ∪ B|, threshold 0.25. It is 1.0 for a re-run of the same lane and ~0.01 for a sparse emission against a dense lattice. The asymmetric fraction is still reported as a diagnostic, because it is what the brief names.

Result for the current file: UNIQUE-VS-REGISTRY across 289 rasters — worst rank correlation −0.065, worst Jaccard 0.030, and the asymmetric maximum of 1.00 attributable to the lattice raster above.

4. The catalogue-based holdout anti-selects novelty — so it is not a score

Measured three independent ways (hypotheses.md, "the validation trap"): a sibling repository measured ρ = +0.087 between its catalogue-hidden proxy and the live leaderboard; its Poisson control (0.098) beats an artifact that scored 0.2778 live (0.019); and this repository's own Poisson control (0.0669) beats the same artifact (0.0067) by 10×.

Consequence, stated in every document that carries the number: the holdout is a bug screen, a leakage canary and a null generator. It is never written as a score, and it is never used to promote or reject a file.

The render/check machinery in scripts/render_doc_pages.py plus tests/test_doc_render.py makes the pair CI-enforced for both lanes' pages.

The rule: a page whose text is not its markdown's text is a defect in the markdown, not a detail. Hand-editing generated HTML is how the first session went wrong (IR-62-02), the pattern survived a merge because the guard was not in main yet, and the fix is one command (render_doc_pages.py PAGE) plus one test that refuses to let the pair drift. When the guard fires on content you did not write, read the other side before you assume the render lost something — here the render was right and the source was short.

One more trap, found the same hour: the page renderer is deliberately minimal and does not escape code spans, so a raw less-than or greater-than sign, or a closing anchor tag, written inside backticks is swallowed as markup and the page loses it silently — this is what happened to the range-check line above, which had to be rewritten with a Unicode ≤. The guard refused to write in both cases, which is the point; the source was rewritten with ≤ and prose instead of angle brackets. Rule: no raw angle brackets in a markdown source that a minimal renderer will pass through. If --check refuses, fix the markdown, not the exception list.

Also fixed while here: the guard itself, which compared word lists. Three legitimate constructs produced false alarms — (0.24073) written as (0.24073), a code span containing a (docs/downloads/.verdict.json), and a full stop that follows a link, which the renderer emits as text plus a closing anchor — because tag boundaries insert spaces on one side only. It now compares normalised character streams (markup, emphasis ticks and punctuation removed on both sides, link targets dropped on the markdown side), and reports the nearest word for context. The deletion-detection test still passes, so the guard is both quieter and unchanged in power.

IR-62-J-08 — the download audit read a session id as a stale hash claim

Found: 2026-10-12, running scripts/audit_downloads.py --write after adding the other lane's file to the manifest. It refused to pass, reporting that docs/index.html "prints hash d0303476 for gems62b-…, whose sha256 starts 42bffef1…" — inside a row I had generated a minute earlier, where the only hex token is the correct 16-char prefix and d0303476 is the lane's session identifier in the verdict text.

Root cause: the cross-check scanned every table row that mentions a file name for \b[0-9a-f]{8,64}\b. Eight hex characters is a normal Git short-id length, and short ids appear in prose about provenance; a gate that fires on prose is a gate people will switch off.

Fix applied: a token counts as a hash claim only at 16+ hex characters and not preceded by / (which excludes arena/d0303476 and paths generally). Any truncated sha printed for a bytes claim is 16 or more in this repo; a stale 16-char prefix is still caught, and the test in tests/test_download_manifest.py covers the file-name-and-bytes matching.

The rule: a consistency gate must not fire on the things a page legitimately says. Encode the claim types you mean to police (digest, byte count, dot count), not every token that looks like one — the value of an audit that runs in CI is exactly its false-positive rate.

IR-62-J-09 — two lanes created the same filename for the same day, and the register has no owner

Found: 2026-10-12, merging origin/main (PR #20, sessions arena/d4d2e53a + arena/778884cc). docs/hypotheses-2026-10-12.md and its .html came back as add/add conflicts: that lane wrote a four-ranked-hypotheses page for 2026-10-12, this lane wrote one too, and git reported 1,000 lines of "conflict" between two documents that never intended to be the same document. The register collision above is the same failure one level down: six documents, three lanes, one shared counter.

Why it was not obvious: docs/ files are named by date, which is a unique key only while one session runs per day. Nothing in the tree declares an owner for IR-62-25 or for hypotheses-2026-10-12.md, and main had moved twice since either branch was cut, so each lane's "next free ID" was computed against a different base.

Fix applied: the numeric IDs are theirs — main is authoritative — and this lane's page is renamed hypotheses-2026-10-12-j.{md,html}, with a cross-reference at the top of each so a reader who arrives from the index finds both rankings instead of assuming the other does not exist. This lane's own entries move to IR-62-J-nn and claim no numbers.

The rule: a date is not an identity. Anything named by a calendar day or by a counter is shared property in this repository; a lane writing a new one appends its lane suffix (-j, IR-62-J-nn) before it commits, not after a conflict. Renaming my side was chosen over renaming theirs for one reason: their page is already cited from main and from the README tree, and re-pointing someone else's citations is the expensive direction.

IR-62-J-10 — a maths block written in LaTeX reached a page with no maths renderer

Found: the same merge. The other lane's docs/index.html explained the metric with $\text{DTI} = \frac{\text{TP}_w}{0.2(\text{TP}_w + \text{FP}_w) + 0.8 K}$ — correct as notation, and rendered by every browser as exactly that string, because no page in this repository loads MathJax or KaTeX. The same block used K for the normaliser where every other document here uses N, and k > for the marginal bar, so the page disagreed with docs/why-h33-scored.md on top of being unreadable.

Fix applied: the block is now plain text (DTI = TP / (0.2·(TP + FP) + 0.8·N), the 4:1 asymmetry named, N used consistently), with their numbers and their argument untouched. Not fixed: adding a maths library to a site that is otherwise dependency-free would cost more than it buys.

The rule: a claim in markup the page cannot render is a claim nobody reads. Pages here are static, dependency-free HTML, so notation is written in the characters the browser already has — ≤, ·, × — or as an inline code span. If a page ever needs real TeX, that is a decision to record here first.

IR-62-J-11 — CI, the test and the renderer each carried their own list of pages to check

Found: 2026-10-12, minutes before committing the merge that renamed this lane's hypotheses page. Local tests were green (92 passed), render_doc_pages.py --check run-card … irregularities … was green, and the audit was green. .github/workflows/ci.yml nevertheless said:

python scripts/render_doc_pages.py --check run-card next-steps irregularities hypotheses-2026-10-12 hypotheses-2026-10-11

That list — hand-copied into the workflow on an earlier day — still named hypotheses-2026-10-12, which after the merge is the other lane's hand-styled page whose markdown this tool refuses to render (their .md is a separate draft with autolinks and a different structure). CI would have failed on a branch that passed every local check, and the fix was not "add --no-verify": it was to stop having three lists.

Why it was not obvious: the three lists were equivalent when written — that is precisely the shape of defect that survives review — and each file justified itself separately: the workflow "just" runs the tool, the test "just" parametrizes over pages, the tool "just" has a default. Nothing said which one is the definition. The workflow's copy also could not express the exemption the merge required, so any attempt to fix CI by editing the workflow alone would have left the test and the tool disagreeing again.

Fix applied: the page list now lives in exactly one place, RENDERED in scripts/render_doc_pages.py, next to HAND_WRITTEN (a dict of page → why it is exempt, because an exemption without a reason is how a drift becomes permanent). tests/test_doc_render.py imports both, --check with no arguments uses RENDERED, CI runs --check with no arguments, and test_the_declared_lists_stay_disjoint_and_honest fails if a page is in both lists, if a declared page has no pair, or if an exempt page has no recorded reason.

The rule: one list, imported; no copied lists in CI. If a workflow names files, it will drift the first time a file is renamed — and a rename is exactly what a collision (IR-62-J-09) forces. When you fix a CI-only failure, ask which of the copies was authoritative, then delete the copies rather than the check.
