Executive summary — how to submit into the competition

Short version: download the GeoTIFF from the top of the site home page, go to the competition's submission page, choose that file, paste the note below, submit. The file is format-legal — all 26 validator checks pass on the bytes read back from disk — and the portal error you hit before (“Predicted values must be in range [0, 1]”) cannot occur for these bytes.

2. Submit it — click by click

  1. Open <https://www.drivendata.org/competitions/306/competition-doe-gems/submissions/> (login required).
  2. New submission → File to submit → Choose file → pick the .tif downloaded above. A .zip containing that single GeoTIFF is also accepted if your browser or network prefers it.
  3. Note (optional) — paste this, it is exactly 126 characters (the stated limit is 140):
   H62-B Lahontan base-level isobase steps/deflections, ridge-relief traced, 37654 isolated dots, >=300 m off catalogue. UNSCORED
  1. Press Create. The organizer scores it on the hidden test set and returns a number.

The number does not exist until step 4. No file in this repository has ever been scored by the organizer. Everything on this site that looks like a score is labelled MEASURED (computed here), OWNER-REPORTED (a score the owner quoted, no receipt), OFFICIAL (quoted from the competition pages) or MODEL (algebra on the published metric). A MODEL number is a projection and is never written as a score.

3. Why the portal once rejected the file — and why it cannot happen here

The error you saw, verbatim: “Predicted values must be in range [0, 1]” [OFFICIAL — the submission form]. The spec asks for a single-band float32 raster with values in [0, 1], matching the CRS, shape and geotransform of the sample submission [OFFICIAL, competition page 967, Submission format]. Two writing habits violate it while looking correct on screen:

mechanismwhy it trips the portalstatus in this file
a float32 nodata sentinel (e.g. -3.4028235e38) written inside the valid footprintthe reader sees an out-of-range floatabsent — outside the footprint we write 0.0
a NaN nodata tag on the bandthe reader returns NaN, which is not in [0, 1]absent — the file carries no nodata tag at all

Both are structurally impossible here: gems62.grid.write_submission writes one code path, then check_submission re-opens the file from disk and re-counts everything. The receipt for the shipped file reports nodata = null, nan_inside_footprint = 0, values_min = 0.0, values_max = 1.0, count = 1, dtype = float32, crs = EPSG:32611, shape = (3730, 3292), transform (100, 0, 243350, 0, −100, 4508550).

4. What the file contains

37,654 isolated single pixels. No two dots are within 300 m of each other (mean self-kernel 0.000, versus 0.032 for the group's champion). No dot is within 300 m of a fault that is already in the USGS/INGENIOUS catalogue — the organizer does not score mapped faults, and the group has an organizer-confirmed +0.0178 (0.2600 → 0.2778) for deleting them. The dots are spread over all six blocks of the grid (block entropy 2.262 bits, versus 2.267 for the champion).
