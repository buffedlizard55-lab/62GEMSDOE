Executive summary — exactly how to make a submission

This page is the whole procedure. Nothing on it requires judgement calls or manual data preparation. If a step cannot be completed automatically it says so and names the blocker.

Step 0 — the file

Download gems62-h62-a-lahontan-isobase-step-38000dots-20261011T201324Z-zeros.tif .zip version

Either form is accepted by the portal: "You can submit a single-band GeoTIFF (.tif) file, or a .zip file containing a single GeoTIFF". The .zip contains exactly one GeoTIFF and nothing else.

Step 1 — go to the submission page

https://www.drivendata.org/competitions/306/competition-doe-gems/submissions/ — sign in, then click New submission. Check the weekly cap shown on that page before you spend a slot; this repository does not spend slots for you.

Step 2 — File to submit

Choose the downloaded gems62-h62-a-lahontan-isobase-step-38000dots-20261011T201324Z-zeros.tif. (The .zip is equivalent.)

Step 3 — Note (optional)

Paste this. It is 75 of the 140 characters allowed:

H62-A Lahontan isobase step/deflection traces; arm A3; 38000 dots; UNSCORED

Step 4 — submit, then record the receipt

The portal returns a score. Copy it into registry/organizer_scores.json next to the submission name and the sha256 above. Until you do that, the score does not exist — nothing on this site may be relabelled ORGANIZER-CONFIRMED from a projection.

Why this file cannot produce "Predicted values must be in range [0, 1]"

That error has two mechanisms and this file closes both. See the front page for the measurement; the summary is:

  1. No sentinel. The float32 nodata value -3.4028234663852886e+38 occurs in 3,061 cells that lie inside the submission footprint in the official feature stack. This artifact writes 0.0 there.
  2. No NaN and no nodata tag. All 12,279,160 cells are finite. The file carries no nodata tag (receipt: nodata = ), so there is no out-of-range value for a validator to find anywhere in the file — inside or outside the footprint.
  3. Values. min 0.000000, max 1.000000; the file is strictly binary {0.0, 1.0}.

What the file contains

38,000 single-pixel dots at value 1.0, at least 3 px apart, every one of them more than 3.0 px from an already-mapped catalogue fault. Median distance to the catalogue 18.9 px; 0.00% within 3 px (must be 0).

How to reproduce this file from scratch

python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
export GEMS62_DATA=/path/to/dir/with/the/three/official/rasters
pytest tests -q                                  # 36 assertions, all published numbers or brute force
python scripts/build_registry.py                 # fetch every earlier raster for the uniqueness gate
python scripts/run_lane.py --budget 38000 --arms A1 A2 A3 --folds 4
python scripts/build_site.py                     # regenerate this site from evidence/*.json

The three official rasters are sha256-pinned and re-verified at the start of every run. 1m_DEM_links.csv and the rasters themselves sit behind DrivenData login; scripts/download_competition_data.sh documents both the login route and the in-organisation git bridge used here.
