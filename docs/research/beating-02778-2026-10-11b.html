2. The arithmetic — this is the explanation

The published index is

DTI = TP_w / (TP_w + 0.2·FP_w + 0.8·FN_w) with a triangular kernel k(d) = max(1 − d/300 m, 0)

[OFFICIAL, competition page 967, quoted in docs/sources.md], implemented and tested in

src/gems62/metric.py (the page's own worked example 3.00/(3.00+0.2·1.89+0.8·2.00) = 0.60 is

reproduced in tests/test_metric.py).

Writing T = TP_w, F = FP_w, K = |G| (hidden truth pixels, so FN_w = K − T):

```

DTI = T / ( 0.2·(T+F) + 0.8·K ) [exact rewriting of the published formula]

```

Three consequences, each of which is a design rule:

(a) A dot is worth placing iff its realised credit k exceeds 0.2·DTI. Adding one unit dot

changes the denominator by exactly 0.2 and the numerator by k, so dDTI > 0 ⟺ k > 0.2·DTI

(src/gems62/metric.py::marginal_bar). For a field already scoring 0.2778 the bar is

0.0556, which corresponds to roughly a 14 % chance of lying within 300 m of a hidden fault

if the offsets are spread over the kernel disc (credit ≈ 0.4·P under that assumption — the

assumption is named because the number depends on it).

(b) At large mass DTI → 5·c where c is the mean credit per dot, because the 0.8·K term

becomes negligible next to 0.2·M. Rank 1 (0.4133, MIRROR-OF-OFFICIAL) therefore implies

c ≳ 0.0827; the top-5 cut-off 0.3333 implies c ≳ 0.0667.

(c) The dependency on mass is explicit and provable. If every dot is isolated (no second dot

inside its kernel) and carries mean credit c:

```

DTI(c, M, K) = c·M / ( 0.2·M + 0.8·K ) = c / ( 0.2 + 0.8·K/M )

```

With the planning value K = 12,000 [INHERITED: docs/research/leaderboard-arithmetic.md

derives K ≤ 13,688 from the 0.26 → 0.2778 thinning; that is a bound, not a measurement]:

4. So: can a submission beat 0.2778?

**Yes, and the condition is exact and checkable — but it is a condition on a quantity this checkout

cannot measure.**

  • Beating 0.2778 requires, at 120,000 isolated dots, a mean per-dot credit c ≥ 0.0778

(≈ 19 % of dots within 300 m of a hidden fault). Reaching the top-5 cut-off 0.3333 requires

c ≥ 0.0933. MODEL, from §2(c); the uncertainty is entirely in c, not in the algebra.

  • The champion already operates at c = 0.1264 (implied), so it is not the mass that is missing

at 37,654 dots — it is either more mass at acceptable credit, or genuinely better placement.

  • This session's field (gems62b-tiltgrad-vote-scarpcorrob-120000-zeros) measures c = 0.0621

per dot on the off-catalogue compilation at 120,000 dots — 95 % of the champion's own 0.0655 on

the same instrument, at 3.2× the mass. Under exact transfer of that instrument the field's

MODEL value is 0.222, i.e. below 0.2778. The pre-registered prediction in the run card is

therefore: this file beats 0.2778 iff its true per-dot credit exceeds 0.0778, and the only

way to learn that number is a submission receipt.

5. What would actually move the line

  1. One ORGANIZER-CONFIRMED number. There is still not one anywhere in this repository. Until

one exists, every comparison here is a proxy argument, and §3 shows proxies cannot rank fields.

  1. A detector with a higher floor of credit, not a larger field. §2(c) makes mass cheap and

quality expensive; the group's own history (0.2778 vs 0.0778 at identical mass) shows quality

spans 3.6× while mass spans ~1.4× within its family.

  1. Stop using the SGMC instrument as a promotion gate, for the measured reason in §3 — and stop

using the segmented catalogue holdout as one: IR-62-HOLDOUT-01 records

Spearman(HOLDOUT-DTI, organizer score) = −0.9141 (INHERITED, lane62-h62a/evidence/), and

this session's own field fails that gate at 0.00073 by construction precisely because it obeys

the leaderboard's own preference for being off the mapped catalogue (−0.60, §3).

  1. What the gate should be instead: a paired test — submit two fields that differ in exactly

one design variable, at the same mass, and let the leaderboard say which is better. The

submission page is the only instrument in this project that measures the target quantity.
