IR-62-TRUNK-01 medium -- pre-existing on main, not caused here open -- reported, deliberately not fixed from this lane

The repository root's own test suite cannot be collected

On a clean checkout of main, `pytest tests/` at the repository root aborts during collection with 2 errors and 0 tests run. `src/gems62/lahontan.py` line 50 does `from .grid import PIXEL_M`, but `src/gems62/grid.py` never defines `PIXEL_M` (it is used at lines 108 and 239 of lahontan.py). Separately `tests/test_metric.py` line 17 imports `brute_force_components` from `gems62.metric`, which that module does not define. This is why the `lane62-ci` GitHub Actions workflow reports failure.

Evidence: Reproduced here after merging origin/main: `pytest tests -q --collect-only` -> 'ImportError: cannot import name brute_force_components from gems62.metric', 'Interrupted: 2 errors during collection', 'no tests collected, 2 errors in 0.36s'. The same failure is visible on main BEFORE this branch merged: Actions run 38173668340 (workflow lane62-ci, on the PR #7 merge commit) completed with conclusion 'failure'. Independently documented as IR-62-11 by the lane62/ session, which also declined to fix it from another lane.

Resolution: NOT fixed from this lane, following the convention lane62/ set: another session's source tree at the repository root is theirs to repair, and two sessions silently editing the same module is how work gets clobbered. This lane's own suite (lane62-h62a/tests, 41 tests) and its CI workflow both pass. Recorded here so the trunk's red build is not mistaken for damage from this merge, and so whoever owns the root lane sees a second independent reproduction with the exact line numbers.

Unblock: In the root lane: define PIXEL_M = 100.0 in src/gems62/grid.py (it is the 100 m pixel size, already implied by the official transform), and either implement brute_force_components in src/gems62/metric.py or drop that import from tests/test_metric.py. Two-line fix, but it belongs to that lane's author.

IR-62-HOLDOUT-01 CRITICAL -- invalidates the promotion gate open -- measured, not fixable inside this repository

The hide-and-recover holdout is ANTI-correlated with the organiser's score

The parallel-run protocol gates every submission on the segmented holdout, and the standing instruction is not to spend a weekly slot on an idea that has not beaten the current holdout best. Scoring 10 ORGANIZER-CONFIRMED artifacts as FROZEN dot masks on one identical holdout shows that gate points the wrong way: Spearman(HOLDOUT-DTI, ORGANIZER-CONFIRMED) = -0.9141 (p = 0.0002), Kendall tau -0.8140 (p = 0.0015). It is not merely a dot-count artefact: the partial Spearman controlling for n_dots is -0.6810 (p = 0.0302), and in 7 of 8 count-matched pairs (|Delta dots| <= 1,500) the file with the LOWER holdout carries the HIGHER organiser score. The cleanest case is h33-h33-2-b2 (37,654 dots, HOLDOUT 0.0053, ORGANIZER 0.2778) against h36-1-rung30-blind-r1 (37,660 dots -- six apart -- HOLDOUT 0.0368, ORGANIZER 0.2710): a 7x holdout difference in the wrong direction.

Evidence: evidence/e9_frozen_artifact_holdout.json, produced by scripts/compare_holdout.py over registry/organizer_scores.json. Mechanism, measured directly: the holdout withholds whole segments of the PUBLIC catalogue and scores their recovery, while the organiser's Initial Prize Round scores a PRIVATE set of faults labelled before the competition. The holdout therefore rewards dots that hug the catalogue and the organiser rewards dots that avoid it. The 0.2778 file was built by DELETING 6,436 dots within 3 px of the mapped catalogue, which raised its organiser score 0.2600 -> 0.2778 and collapses its holdout DTI 0.1322 -> 0.0053. Our own artifact has zero dots within 3 px of any catalogue pixel (minimum distance 3.2 px, median 18.9 px), so its frozen HOLDOUT-DTI is exactly 0.0000 -- by construction, not by failure. The same is true of the winner.

Resolution: NOT papered over and NOT worked around. The run card's verdict is 'negative' and the artifact is marked ok_to_submit = false, because the repository has no valid instrument with which to justify spending a slot. The E3 arm-A3 number (0.1224) remains a correct measurement of the PROCEDURE under per-fold visible-only pruning, and is reported as such, but it is no longer presented as a promotion argument. Fixing the gate needs a hidden truth set that is not the public catalogue, which this sandbox cannot obtain.

Unblock: Either (a) obtain the organiser's private label set -- not public -- or (b) accept that selection between off-catalogue artifacts is a human judgement informed by the ORGANIZER-CONFIRMED budget ladder, not a holdout decision. Option (b) is what the protocol already implies when it says promotion is a separate selector step.

Source for manual review: https://www.drivendata.org/competitions/306/competition-doe-gems/page/967/

IR-62-DEM-01 high open -- worked around

No absolute-elevation band exists in the official feature stack

The lane is specified as 'map shoreline benches in the DEM'. training_features.tif has 19 bands and the only topographic ones are band 12 'Detrended elevation - topography with regional trends removed' and band 19 its slope. A Lahontan isobase is an ABSOLUTE elevation datum, so the detrending operator removes part of the signal the lane needs. Verified by reading the band DESCRIPTION tags from the sha256-pinned file itself.

Evidence: evidence/e0_data_verification.json -> spec.band_descriptions

Resolution: The isobase is fit in detrended-elevation space (6 km Gaussian through the pluvial-lake-margin band) and the flags are residuals against that fit. A smooth detrend and a smooth isobase tilt are degenerate at long wavelength, so the fit absorbs the unknown trend and the residual keeps the short-wavelength step signal. The absolute shoreline elevation (the ~1177 m class number) cannot be used and is not claimed anywhere on this site.

Unblock: 1m_DEM_links.csv from the DrivenData data tab, or USGS 3DEP directly. Free, public domain. Not reachable from this sandbox.

IR-62-SENTINEL-01 high closed -- root cause of the portal error

3,061 cells inside the submission footprint carry the float32 nodata sentinel

training_features.tif uses -3.4028234663852886e+38 as nodata. Re-measured here: 7,113,308 cells carry it, and 3,061 of those lie INSIDE the submission footprint (sample_submission.tif is finite there) in all 19 bands; band 6 'tc' has 12 extra (3,073). Writing those values through unchanged puts cells outside [0, 1] and the portal returns 'Predicted values must be in range [0, 1]'.

Evidence: evidence/e0_data_verification.json -> spec.sentinel_cells_inside_footprint = 58,171 (= 19 bands x 3,061 + 12)

Resolution: submission_writer.py writes an all-finite artifact: zeros outside the footprint, no nodata tag, every one of the 12,279,160 cells finite and in [0, 1]. validate.py re-opens the bytes from disk and asserts it. This is the form the group's organiser-confirmed 0.2778 file was shipped in.

Unblock: none needed

IR-62-BENCH-01 medium closed -- bug found and fixed in this session

The bench mask circularly excluded the residuals it was meant to flag

The first implementation of bench_pixels() required |elev - isobase| to be below the 60th percentile of the in-band residual, and flag_steps() then looked for residual outliers inside that set. The two conditions are contradictory: the run produced n_steps = 0 over the entire 5.17 M-pixel footprint.

Evidence: first run: n_bench=230,025, n_steps=0, step_threshold_m=127.7

Resolution: bench_pixels() is now geometric only (margin band + slope window + plan curvature percentile). The residual test lives solely in flag_steps(). tests/test_gems62.py::test_bench_pixels_no_longer_excludes_large_residuals asserts the regression cannot return.

Unblock: none needed

IR-62-STEP-01 medium closed -- measured and corrected

An unbounded isobase-residual outlier test selects DEPLETED terrain

Flagging steps as 'residual > k * MAD' keeps exactly the pixels the lane should reject. Measured catalogue enrichment by |isobase residual| inside the bench band: 2.26-2.77x below 210 m, then 1.45x at 210-260 m, 1.16x at 260-320 m, 0.66x at 320-400 m, and 0.00x above 400 m (403 px, not one mapped fault). The unbounded k=2.5 flag scored 1.21x over 14,586 px -- below the 2.44x of the bench band it was drawn from.

Evidence: evidence/e2_enrichment.json

Resolution: flag_steps() takes a bounded throw window [15, 130) m. The bounds have an independent physical meaning: a structure offsetting the ~15 ka highstand at 1-8 mm/yr accumulates 15-120 m of throw in 15 kyr, which brackets the slow-to-fast range of Great Basin faults. Below ~15 m the step is under what a 100 m pixel can express; above ~130 m it is the range front or a canyon head, not a displaced shoreline.

Unblock: none needed

IR-62-EXT-01 medium closed -- bug found and fixed in this session

Trace extension walked across the structure instead of along it

extend_traces() originally derived its walk direction from the gradient of the smoothed evidence field, on the argument that evidence ridges run along the structure. On this data that direction is far too noisy: median trace length 1 px, mean 2.4 px -- the traces never extended at all.

Evidence: first run: n_traces=1,943, traced_px=3,801, len_mean=2.4, len_median=1

Resolution: The walk direction is now the strike of the fitted isobase (local_strike()), which is well posed, and the evidence field is used only as the stopping criterion -- which is what the lane text actually says. tests/test_gems62.py::test_extend_traces_walks_along_strike_not_across_it asserts a north strike yields a north-south trace and no east-west motion.

Unblock: none needed

IR-62-NMS-01 low closed -- bug found and fixed in this session

The greedy dot thinning was O(k^2) and could not finish a fold

_greedy_thin() compared each candidate against a growing Python list via np.asarray(taken_y), which is O(k^2): at a 38,000-dot budget that is ~1.4e9 element conversions per holdout fold.

Evidence: code inspection; the first holdout run did not complete a fold

Resolution: Replaced with a spatial hash of cell size min_sep, O(1) amortised, with an early break at the budget.

Unblock: none needed

IR-62-HOLDOUT-01 high open -- structural, cannot be fixed here

The holdout's truth is the visible catalogue, so it cannot reward a new fault

The competition's hidden test set is a set of faults NOT in the USGS/INGENIOUS catalogue. Every holdout in this repository can only score against catalogue faults, and this lane's whole premise is that it finds structures the catalogue is missing. A holdout win is therefore necessary but not sufficient, and a holdout loss does not prove the lane wrong.

Evidence: same limitation recorded as IR-32-PROXY-01 in buffedlizard55-lab/GEMSDOE32

Resolution: Reported, not hidden. Every score on this site is labelled HOLDOUT-DTI and carries the evaluator version, the withheld-positive count and a 95% CI. No projection is ever written as a score.

Unblock: the organiser's hidden label set, which no participant has

IR-62-DEFL-01 low open -- honest negative

Lateral deflections along strike carry no catalogue enrichment at 100 m

The lane asks for 'abrupt steps OR lateral deflections along strike'. The azimuth-kink flag (>22 deg over 3 px) selects 1,173-4,399 px and measures 1.12x enrichment -- at the footprint mean, i.e. no signal. Broken out by habitat it is 0.75x, 1.42x, 0.90x, 0.52x across habitat bins: inconsistent.

Evidence: measured in this session; recorded in evidence/e1_lane_surfaces.json

Resolution: Kept in the emission as low-priority seeds because the lane specifies them, but they contribute ~0.4% of the flag set and are not relied on. The finding is reported rather than quietly dropped.
